# 版本演进与开发日志

这份日志只记录会影响后续决策的事实：每个阶段解决什么问题、为什么返工、用什么门禁收口、最终处于什么状态。它不堆命令流水，也不把“代码可部署”“已 push/tag”“已上线”混成一个词。

## 状态口径

- **代码可部署**：本地实现、focused 测试、typecheck/build 和审计达到门禁，但还没有远端版本。
- **已 push/tag**：分支和不可变 annotated tag 已通过普通 non-force Git transport 推送并远端回读，生产未必变化。
- **已上线**：生产即时备份、服务器副本/loopback、原子切换、浏览器和运行资产不变量均通过。

内部追溯可以记录 commit/tree/tag object，但 SHA 不能替代用户侧验收。

## v1.3.4：安全边界维护

**版本事实**：commit `7c76e2de0c26f6b65b97cbd9fa0b6798352c00bc`，tree `b182f8005d0cbb6b10ac1014ddde4633be4a90c5`。

### 第二轮审计发现

- `payload.findGlobal({ draft:true, overrideAccess:false, user:null })` 仍返回草稿，因为 Local API 的 draft 是独立 args，不在 req.query/url；
- 名称合规的 SQLite symlink 可指向隔离根外，guard 仍会写外部数据库。

- 三个 Global 共用 beforeOperation，直接检查 `args.draft` 和 `overrideAccess`，匿名/停用/删除/查询异常 fail closed；

- 公开写在完整 body 解析前同时检查声明长度和流式真实长度；不信任伪造 XFF；
- active user 每次按数据库事实重验，旧 JWT/cookie 不能绕过停用。

## 跨版本永久规则汇总

1. 从页面字段消费矩阵开始，不从 Collection 字段堆砌开始。
2. 角色口语必须映射到正式 role；UI、API、Collection、文件分别验收。
3. 中文生产数据是英文同步权威；source unavailable/stale 写前失败。
4. 英文禁止中文 fallback，跨语言使用 stable source identity。
5. 置顶、资源位、featured、显式排序优先，发布时间最低。
6. 导入、发布、快照各阶段都要原子、幂等、可故障注入。
7. 底层 UTC，显示和自然日按 Asia/Shanghai。
8. 从 schema 隐藏字段不等于 drop 历史列。
9. 浏览器验收覆盖真实 DOM、移动端、network、console、media 和权限。
10. 安全测试覆盖 REST、Local API、旧会话、chunked body、symlink/hardlink。
11. 代码、SQLite、public media、private、env 和备份是不同资产。
12. 普通 non-force push、不可变 tag、远端回读和生产原子切换缺一不可。
13. 当前不使用 publisher、wrapper、dry-run、doctor 或部署锁。
14. P2 必须如实登记：招聘附件原子性、Form Builder 匿名 create、prebuild 在线生成、历史账号 fail-open 均未完成。

## 跨版本专题复盘一：从“有字段”到“字段有消费者”

v1.0 至 v1.2 的主要工作是把静态站转成运营可编辑站点。这个阶段最容易用 Collection 字段数量衡量进度：后台能录入、API 能返回，就被认为动态化完成。后续实际联动证明，字段还可能在 BFF、显示适配、页面种类或排序中没有正式位置。v1.3 的 relatedNews 和 comparator P1 是同一类问题的更晚表现：代码片段存在，但消费链没有闭合。

此后每个版本都要求列出字段从后台到页面的路径。V1.3.1 删除六个死字段不是简单“精简后台”，而是消费矩阵成熟后的结果。永久规则是字段设计必须同时给出录入者、published/draft、API、ViewModel、页面、排序/关系和删除策略；测试要命中正式入口。字段越少并不天然更好，真正标准是每个字段都能解释且可验证。

## 跨版本专题复盘二：从角色界面到真实 ACL

v1.2 建立双模式后台后，项目拥有了运营视图和全功能视图，但也形成一个隐患：界面称呼、代码 role 和 helper 名称并非总能一眼对应。v1.3 把“管理员可删除、运营不可删除”理解反，说明即使已有权限系统，需求翻译仍可能失败。v1.3.1 纠正的不只是一个布尔条件，而是完整链路：三角色 UI、直接 DELETE、二次确认、孤立 resume/private 清理、共享文件和失败一致性。

v1.3.4 又进一步证明 `req.user` 存在不等于当前账号仍 active。权限必须在导航、按钮、Collection、REST/Local API、private 文件和账号生命周期六个视角验证。此后所有权限需求先输出显式矩阵，再改代码；任何“管理员”“正式内容角色”或历史 helper 名称都要用实际 role 值解释。

## 跨版本专题复盘三：英文发布从功能完成到可证明正确

v1.21 建立英文独立内容、provenance、release 和 snapshot，是架构上的主要跃迁。v1.21.1 处理生产中文资料漂移，强调来源必须在切换前重新读取。v1.21.2 说明内容正确不代表移动端布局正确。到 v1.3 独立审计又发现 importer 事务、幂等和律师 snapshot fallback，表明发布末端原子不等于整个链路原子。

最终方法把每个阶段分别门禁：来源获取写前失败；importer 单批事务；等值输入零写；release 验证四个 Globals、全部条目、关系和媒体后原子发布；snapshot 无中文/private 泄漏；route map 使用 stable source identity；浏览器检查英文移动端。当前 prebuild 在线重生成仍保留 P2，说明文档需要同时记录成熟能力和未完成边界，不能用“英文已上线”覆盖风险。

## 跨版本专题复盘四：视觉问题为何需要版本纪律

v1.21.2 的 390 溢出、v1.3.1 至 v1.3.3 的 Hero 指示器、v1.3.5 的 Footer 两项都属于视觉范围。它们共同说明：视觉修改可能只有几行，却依赖真实 DOM、伪元素、共享 locale 节点、viewport 和交互逻辑。删除一条横线时必须区分 Hero 进度和导航当前页下划线；对齐桌面 Footer 时必须避免移动端和英文；扩大 anchor 时必须保持 href/target/rel。

小改不意味着可以修改 main 或移动旧 tag。每次仍应从不可变基线形成最小 diff、focused 契约和独立版本。视觉回归强度与用户要求和风险相称，但一旦部署，真实生产页面仍需确认。版本日志因此记录“两个文件 +8/-2”这样的范围证据，而不只写“Footer 优化”。

## 跨版本专题复盘五：安全审计怎样发现实现者看不到的问题

v1.3.4 第一轮实现已经处理 draft、active user、body limit、XFF 和 seed guard，普通源码审查容易认为完整。独立审计从框架真实行为出发：Payload Local API 把 draft 作为独立 args；文件系统可以通过 symlink/hardlink 改变真实目标。这两个 P1 都位于实现者原先抽象边界之外。

第二轮修复没有重写认证或 seed 系统，而是在最接近真实 operation 和文件系统的边界 fail closed。测试也不只断言错误码：Global 用真实 `payload.findGlobal`；旧会话真实登录后停用；seed 失败对比目标文件 hash、mtime、size 和 schema。此后安全审计的价值被定义为“尝试突破实现假设”，而不是重复运行实现者已经提供的 happy path。

## 跨版本专题复盘六：数据清理与代码发布为何分开

V1.3.1 同批包含关闭预约发布配置和定向清理三条过期 schedulePublish job。配置变更进入源码 diff；生产 job 清理只在即时备份和明确授权后执行，不进入 Git。清理前只记录非敏感元数据和数量，清理后证明内容表、版本表、发布状态和更新时间未因任务删除改变。

同理，六个死字段从 admin/API schema 移除，但历史列保留。代码目标、运行数据动作和物理 schema 不是一回事。版本日志必须分别写“源码改了什么”“生产定向做了什么”“哪些物理数据没动”。这种分层能防止开发者为了让 diff 看起来完整而引入破坏性 migration，也能防止数据清理没有审计记录。

## 跨版本专题复盘七：Git transport 与版本语义

多个版本都要求普通 non-force push 和不可变 annotated tag。v1.3.5 的 HTTPS 超时是一个有价值的例子：网络 transport 可以失败，但不能因此改用 GitHub Git Data API 手工制造 commit/ref/tag，更不能 force 或假报成功。最终通过正常 SSH Git transport完成，仍保留 ancestry、普通 push 和远端回读语义。

远端回读必须同时确认 branch SHA、commit tree、tag object、peeled commit 和 peeled tree。这样能发现 tag 指错、轻量 tag、远端分支漂移或本地未推送。生产部署只接受已回读的不可变版本。Git 收口是上线的前置证据，不是上线本身。

## 跨版本专题复盘八：生产事实不能从仓库脚本推断

项目历史中 release 目录、current symlink、共享 SQLite/media/private 和 env 文件可能随着部署演进。仓库旧 runbook 或脚本只能说明曾经的意图，不能证明当前生产实际布局、所有者和权限。每次部署前只读核对当前 release/symlink/env 位置和权限，但不读取 env 值、数据库记录或 private 内容。

生产切换以线上 SQLite、public media、private 和 env 为唯一权威，新 release 只带代码和经过授权的静态产物。即时备份、服务器副本、loopback、并发写保留和原子切换缺一不可。若只读链路不稳定，不应把文档任务扩大成生产审计；使用已经验证的发布回报事实并明确证据边界即可。

## 跨版本专题复盘九：如何写下一版本日志

下一版本先写目标和明确不做项，再写权威基线 commit/tree/tag。实现中记录 consumer/access/route/proxy 事实、changed-files allowlist 和失败复现。完成后记录 focused、type/build、DB、浏览器、敏感资产与独立审计。Git 和生产分别记录状态，不使用“已完成”模糊带过。

事故只保留有复用价值的四部分：根因、实际影响、为什么原门禁没发现、永久规则。不要复制敏感终端日志，也不要用大量命令淹没决策。延期项要标优先级和边界，未经授权不夹带。只有这样，版本日志才能帮助下一位同事做得更好，而不是成为一份无法执行的历史流水账。
