# 给同事的使用说明

这套文件不是一份“项目总结”，而是一套可以继续工作的交接工具。它把卓建官网从 Payload 安装、内容建模、前后端接线、双语发布、安全修复到 V1.3.5 的实际经验拆成三层：先让第一次接手的人知道项目现在是什么样，再让开发人员理解为什么这样设计，最后提供一套可复制到其他客户项目的 Skill、表格和检查清单。

生成日期：2026-07-19。事实基线：不可变版本 `v1.3.5`，commit `add4e5d0b0ba04778a500ef4281255c65c723120`，tree `6c593e879bb71468c76e53f677931687887ba8a4`。

## 10 分钟快速上手

如果你只有 10 分钟，按这个顺序读：

1. 先读本文件，弄清楚哪些是事实、哪些是建议。
2. 打开 [04_交付清单与检查表.md](04_交付清单与检查表.md)，看项目从需求到上线需要哪些证据。
3. 产品或运营继续读 [01_卓建官网从Payload安装到V1.3.5_复盘与开发偏好.md](01_卓建官网从Payload安装到V1.3.5_复盘与开发偏好.md) 中的“用户偏好”和“字段消费矩阵”。
4. 前端或后端继续读 [02_前端架构与开发规范.md](02_前端架构与开发规范.md)，重点看数据流、路由、排序、媒体和公开写接口。
5. 需要追溯某次返工时，查 [03_版本演进与开发日志.md](03_版本演进与开发日志.md)。
6. 要在新客户项目复用方法时，使用 [payload-client-website-development/SKILL.md](payload-client-website-development/SKILL.md)，并从其 `templates/` 复制空白模板。不要直接复制卓建的角色、栏目、域名或数据。

## 哪些可以直接复制

可以直接复制的是“问题结构”和“验收表”，不是业务答案：

- `templates/需求访谈问卷.md`：用于第一次访谈和需求冻结。
- `templates/页面字段消费矩阵.md`：用于证明一个字段到底被谁编辑、谁读取、在哪里展示或排序。
- `templates/角色权限矩阵.md`：用于把口语中的“管理员”拆成真实 role、UI、API 和资源访问。
- `templates/Collection_Global设计表.md`：用于建模前先对齐单例配置和条目集合。
- `templates/测试验收矩阵.md`、`templates/独立审计清单.md`：用于上线前门禁。
- `templates/发布回滚清单.md`：用于区分可部署、已推送和已上线。
- `templates/开发日志模板.md`、`templates/交接包模板.md`：用于记录决策，不堆命令流水。

以下内容必须按新项目重新确认：栏目名称、角色值、权限范围、排序优先级、资源位、域名、反向代理链、数据库位置、媒体目录、env 布局、发布方式、双语覆盖率、是否允许 fallback、法规或隐私要求。卓建的 `super-admin/admin/operator`、中文线上数据权威、英文无中文 fallback、SQLite 和静态英文快照都是项目事实，不是 Payload 的默认真理。

## 推荐的工作顺序

### 1. 先冻结“页面怎样消费内容”

不要从建 Collection 开始。先列出页面、区块、列表、详情、首页资源位、搜索、语言切换、相关内容、媒体和日期。每个字段都要回答：谁录入、谁读取、是否显示、是否排序、是否参与关系、是否有 fallback、删除后怎样处理。

产物：页面清单、页面字段消费矩阵、内容来源图、非功能需求和明确的“不做清单”。

### 2. 再定义后台和权限

后台应按前台栏目和运营任务组织。先给每个角色写正式 role 值和一句职责，再逐项列 UI 是否可见、Collection 是否可读写、API 是否允许、文件能否访问。不要因为页面按钮隐藏就认为权限已经完成，也不要把用户口语中的“管理员”直接映射到代码中的 `admin`。

产物：角色权限矩阵、后台导航草图、Collection/Global 设计表、媒体与私有附件清单。

### 3. 建立数据与运行资产边界

区分源码、数据库、公开媒体、私有附件、env、备份和构建产物。明确谁是权威源、迁移由谁执行、什么不能进 Git、生产切换如何保留并发业务写入。SQLite 不是一个可以随发布包覆盖的普通文件。

产物：迁移与运行资产清单、备份/恢复演练记录、数据库 quick check/FK 检查方案。

### 4. 实现 Payload 与独立前端

Payload 负责内容模型、草稿/发布、访问控制、媒体和管理后台；独立 Next 前端通过 BFF 和显示适配层消费稳定契约。BFF 不应偷偷丢字段，显示适配层不能出现多个并行真相，页面组件不应直接猜 Payload 原始结构。

### 5. 双语单独建账

每条翻译都要有来源记录、字段路径、源文本哈希、审核状态和稳定路由映射。同步必须写前检查 stale，批次失败全回滚，相同输入重跑零写。英文缺对应内容时要按产品规则回英文首页，不能悄悄显示中文。

### 6. 先测行为，再测页面

类型检查和构建只能证明代码能编译。还要测权限正反例、事务回滚、公开写超限、私有文件隔离、路由映射和排序真实输出。最后用真实浏览器检查桌面、移动端、console、network、broken media、overflow 和后台操作。

### 7. 把发布分成三个状态

- **代码可部署**：本地审计和验证通过，尚未远端收口。
- **已 push/tag**：远端分支和不可变 tag 已回读，仍未上线。
- **已上线**：生产备份、演练、原子切换和线上浏览器验收均完成。

任何一个状态都不能替代下一个。版本号、HTTP 200 或进程存在也不能单独证明上线成功。

## 一次完整交付应包含什么

最小交付包应包含：

- 已确认需求与明确不做项；
- 页面清单、字段消费矩阵、角色权限矩阵；
- 数据模型和前后端契约；
- 公开/私有媒体边界；
- 双语来源、映射、审核与快照清单；
- 迁移、运行资产、备份和回滚清单；
- focused、typecheck、build、数据库和浏览器证据；
- changed-files allowlist 和敏感资产检查；
- 版本 commit/tree/tag 与远端回读；
- 生产切换、回滚点和上线后的真实页面证据；
- 给运营的日常操作说明和权限边界。

## 常见误区

### “后台能看到就代表可用”

不对。字段可能没有前端消费者，按钮可能只在 UI 隐藏但 API 仍可调用，关系可能被 mapper 生成后又被显示层清空。必须沿录入、存储、API、适配、页面和权限逐层验证。

### “publishedAt 就应该决定顺序”

不对。卓建的置顶、首页推荐、栏目资源位、显式 `sortOrder` 和推荐位都比发布时间优先；`publishedAt` 只在允许的并列情况下作为最低优先级。改变 comparator 的调用位置可能破坏运营排版。

### “做了英文版就是把中文翻译后复制一份”

不对。英文是独立发布内容层，必须有 provenance、stale 检测、事务、媒体映射、稳定 sourceRecordId/route 和无中文 fallback 规则。

### “删除后台字段就是删除数据库列”

不对。V1.3.1 的六个零 consumer 字段只从 Payload admin/API schema 移除，历史列保留，避免生产隐式 drop。用户可见目标、API 契约和物理迁移是三件事。

### “HTTP 200 就完成了”

不对。页面可能空白、布局溢出、关系链接错误、媒体 404、旧会话越权或移动端伪元素仍占空间。需要行为和浏览器证据。

### “顺手把附近问题也修掉”

客户维护最怕范围漂移。每个批次先定义 changed-files 和业务 allowlist；发现第三类修改需求就暂停回报。已知技术债可以登记延期，但不能伪装成当前补丁的一部分。

## 使用这套材料时的边界

本文件夹不包含密钥、cookie、密码、env 值、生产数据库记录或私有附件内容。公开路径、字段名、角色名和版本 SHA 只用于可审计追溯。生产目录或 symlink 布局若没有当次只读证据，应标注“待现场核对”，不要从旧脚本推断当前事实。

本包也不是替代源码的第二套规范。当前实现以 V1.3.5 源码为准；早期数据契约和旧复盘只能提供历史背景。遇到冲突时，应回到 tag、当前访问控制、路由、测试和真实运行环境核对。

## 第一次接手时的一天怎么安排

上午不要急着启动所有服务。先确认自己处理的是需求、前端、CMS、内容、审计还是部署，并记录当前不可变版本。浏览目录时只看与目标有关的入口：产品看页面和矩阵，前端看 App Router、BFF、display-data 和 Shell，后端看 config、Collection/Global、access、hook、脚本和集成测试。不要递归扫描数据库、media、private、备份或旧工作树。

随后选择一个公开页面做纵向追踪：从后台字段找到 Payload schema，从 published API 找到 BFF mapper，再找到 ViewModel 和页面。选择一个权限动作做横向追踪：从 Admin 按钮到 Collection access、自定义 route、内部 hook 和文件。完成这两条追踪后，你会比只读 README 更快理解项目的真实边界。

下午用隔离环境跑轻量验证：现有 focused tests、typecheck 和目标模块构建。不要为了熟悉项目执行正式 import、release、snapshot 重生成或 seed；这些脚本有各自输入和运行资产门禁。需要看生产时只核对当前 release/symlink/env 布局等非敏感事实，不读取 env 值、数据库记录或 private 内容。

当天结束前写三段话：已确认事实、仍不确定事实、任何修改前必须取得的输入。这样第二天进入实现时，不会把假设写进 schema 或权限。

## 产品同事怎样提出一个可执行需求

先写用户在哪里看到问题、做什么动作、期望看到什么结果。例如“普通管理员在投递列表每行看到删除，运营不看到；普通管理员直接 API 删除成功并清理孤立附件，运营直接调用返回 403”，比“管理员可以删简历”准确得多。

再写不能改变什么：是否保持草稿和发布、是否不改英文、是否不碰移动端、是否保留资源位。最后写验收环境和证据：桌面/移动、哪几个角色、是否需要真实浏览器、是否涉及生产数据。涉及“最新”“管理员”“上线”“同步”的词必须补充正式定义。

产品不需要提前决定技术文件，但应决定业务 fallback、删除后果、排序优先级和语言缺失行为。开发可以选择实现路径，却不能替用户发明这些产品规则。

## 前端同事怎样避免只修表面

收到视觉问题先定位真实 DOM 和数据来源。一个看似 CSS 的问题可能来自空字段、错误关系、伪元素、共享英文组件或 BFF 排序。确认后用最窄 selector 和最小文件完成，检查是否影响相邻 viewport、locale 和交互。

新增页面不要直接 fetch Payload；先扩 BFF 契约和唯一显示适配。新增关系不要只渲染标题；使用稳定 route 并覆盖 target 缺失。新增日期不要复制格式化函数；使用统一上海时区边界。任何 fallback 都要标明来源和适用环境。

前端验收除了页面截图，还要看 console、network、broken image、scrollWidth、直接 URL、刷新、返回和语言切换。HTTP 200、组件渲染或 snapshot 文本匹配都不能单独代表用户流程通过。

## 后端同事怎样避免把 Payload 当普通 CRUD

每个 Collection/Global 都要写草稿、发布、access、关系、媒体和删除生命周期。Payload 的 REST、Local API、Admin 操作和 hook 可能携带不同参数；安全边界要在真实 operation 层测试。使用 overrideAccess 的内部动作必须明确目标和范围，不能把它变成角色直接权限。

涉及 SQLite 时先区分 schema 配置、生成类型、migration 和生产历史列。用户要求后台不显示字段，不自动等于物理删列。脚本涉及导入或 seed 时，在 Payload/config/数据库初始化前验证隔离目标；事务、故障回滚和相同输入零写是正式写脚本的基本要求。

公开写 route 必须在完整 body 缓冲前做声明长度和流式实际长度上限。客户端地址只能来自已确认的可信代理语义。private 文件不进入公共 media、快照、日志或测试证据。

## 运营同事怎样判断“改了为什么没生效”

先确认记录是草稿还是已发布，修改的是正确栏目和正确语言。再看是否有资源位、featured、置顶或 sortOrder；发布时间通常不会覆盖这些显式安排。关系内容还要确认目标本身已发布，英文关系还需要对应翻译和 route。

图片应先在素材中心上传并选择，不要把本地路径粘进文本。富文本尽量使用后台提供的有限格式，不从 Word 带入复杂样式。删除投递或附件前看二次确认；无权限的按钮不会显示，直接 API 也会被服务端拒绝。

如果后台已发布而前台仍不对，记录页面、记录名称、操作时间和期望结果即可，不要截图或复制 private 简历、个人信息、cookie 或 env。开发会沿 published API、BFF、显示适配和缓存边界排查。

## 审计同事怎样找到“看起来都写了”的漏洞

不要只读新增函数和新增测试。先从用户入口反向追踪到配置：页面是否真的消费字段，API 是否真的调用 comparator，Local API 是否走同一个 draft 判断，Admin 隐藏是否有 ACL。再构造实现者可能没想到的真实形态：停用后的旧会话、无 Content-Length 的 chunked 请求、伪造多跳 XFF、symlink/hardlink、共享附件、第 N 条写入失败。

每个失败不仅看错误码，还看不变量：记录、版本、updatedAt、数据库文件、物理附件、公开内容和工作树是否变化。审计发现 P0/P1 时冻结 Git 和生产，只允许阻断项定向修复；复审还要确认已通过范围和 changed-files 没有漂移。

## 项目负责人最后签字前要问的十个问题

1. 当前结论是可部署、已 push/tag 还是已上线？
2. 页面字段和后台字段是否存在一一可解释的消费关系？
3. 每个正式 role 的 UI/API/private 权限是否都有正反例？
4. 置顶、资源位、显式排序是否没有被“最新优先”覆盖？
5. 双语是否以最新权威源同步且无跨语言 fallback？
6. SQLite、public media、private 和 env 是否仍使用生产权威资产？
7. 公开写接口是否覆盖 chunked 超限和伪造代理头？
8. 浏览器是否验证目标页面、viewport、console、network 和链接？
9. Git 是否普通 non-force，annotated tag 是否远端回读？
10. 延期 P2 是否如实列出，没有被写成已经解决？

这十问全部有证据，才说明交付不仅“做过”，而且下一位同事可以安全接手。
